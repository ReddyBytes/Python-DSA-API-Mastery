# 🎯 WebSockets & Real-Time APIs — Interview Preparation

> This file prepares you to discuss WebSockets and real-time APIs like a working engineer.
> Not just definitions — but real-world usage, trade-offs, and production scenarios.

# 🔹 Basic Level Questions (0–2 Years)

**Q1: What is a WebSocket and how does a connection get established?**

<details>
<summary>💡 Show Answer</summary>

A WebSocket is a persistent, bidirectional TCP channel between a client and server. It starts as a regular HTTP request: the client sends an HTTP `GET` with `Upgrade: websocket` and `Connection: Upgrade` headers. If the server supports WebSockets, it responds with `101 Switching Protocols`. After that, the HTTP connection is "hijacked" — it is no longer HTTP but a raw TCP channel using the WebSocket framing protocol (RFC 6455). Either side can now send messages at any time without the overhead of a new HTTP request. The connection stays open until one side sends a close frame or the TCP connection drops.

</details>

<br>

**Q2: What is the difference between WebSocket and SSE (Server-Sent Events)?**

<details>
<summary>💡 Show Answer</summary>

WebSocket is bidirectional — both the client and server can send messages at any time over the same persistent connection. SSE is one-directional — the server can push events to the client, but the client cannot send data over the same connection (it would use a separate HTTP request). WebSocket is best for chat, collaborative editing, or gaming where both sides send data frequently. SSE is best for notifications, live dashboards, and progress feeds where only the server needs to push. SSE is simpler to implement, works over standard HTTP, supports automatic reconnection built in, and does not require sticky sessions in the same way. SSE is text-only; WebSocket supports binary frames natively.

</details>

<br>

**Q3: What are WebSocket close codes and what does code 1006 indicate?**

<details>
<summary>💡 Show Answer</summary>

Close codes are numeric codes sent in the close frame to indicate why the connection ended. Key codes: 1000 is normal closure (clean shutdown), 1001 is going away (server shutting down or browser navigating away), 1008 is policy violation (e.g., failed authentication), 1011 is internal server error. Code 1006 is special — it indicates abnormal closure where no close frame was sent. This happens when the TCP connection drops abruptly (network failure, crashed client, NAT timeout). You cannot explicitly send a 1006; it is generated by the WebSocket library when it detects a dropped connection without a proper handshake close.

</details>

<br>

**Q4: How do you authenticate a WebSocket connection?**

<details>
<summary>💡 Show Answer</summary>

Two main approaches. First, token in the query parameter: the client connects to `wss://api.example.com/ws?token=jwt`. The server reads the token from the query string before accepting. Simple to implement but the token is visible in server access logs. Second, token in the first message: the server accepts the connection, immediately waits (with a short timeout) for an auth message containing the token, validates it, and either proceeds or closes with code 1008. This is cleaner for production. You cannot use standard HTTP headers for authentication in browser WebSocket connections — the browser WebSocket API does not support custom headers at connection time. The query parameter or first-message pattern works around this limitation.

</details>

<br>

**Q5: What is the ping/pong mechanism in WebSocket and why is it needed?**

<details>
<summary>💡 Show Answer</summary>

Ping/pong are control frames defined in the WebSocket protocol. The server sends a ping frame; the client must respond with a pong frame automatically. This serves as a heartbeat to detect dead connections. Without it, a TCP connection can remain open at the OS level even after the client has crashed or disconnected behind a NAT (the OS has not yet detected the dropped connection). NAT gateways also drop idle connections after a timeout (often 30–60 seconds) without warning. By sending pings every 20–30 seconds, the server detects clients that no longer respond and cleans up the connection and associated resources. If no pong arrives within the timeout window, the server closes the connection.

</details>

# 🔹 Intermediate Level Questions (2–5 Years)

**Q6: How do you broadcast a message to all clients in a room when your WebSocket server runs as multiple instances?**

<details>
<summary>💡 Show Answer</summary>

Each server instance holds only the WebSocket connections local to it. Broadcasting via an in-memory `ConnectionManager` only reaches clients on that same instance. The solution is Redis pub/sub as a shared message bus. When a server needs to broadcast to a room, it publishes the message to a Redis channel named `room:{room_id}`. Every server instance subscribes to the channels for rooms that have local connections. When a message arrives on the Redis channel, the instance forwards it to its local connections in that room. This way, a message published by any instance reaches all clients in the room regardless of which instance they are connected to. The Redis pub/sub pattern scales horizontally without coordination between instances.

</details>

<br>

**Q7: What does "sticky sessions" mean in the context of WebSocket load balancing, and how do you avoid needing them?**

<details>
<summary>💡 Show Answer</summary>

Sticky sessions (also called session affinity) mean the load balancer consistently routes a client to the same backend instance for the duration of their WebSocket connection. This is needed because a WebSocket connection is stateful — the connection state (auth, subscriptions, room membership) lives in the server process that accepted the connection. Without stickiness, reconnects might land on a different instance that has no record of the client. You avoid needing sticky sessions by externalizing all connection state to Redis: room memberships, subscriptions, and user identity are stored in Redis rather than in process memory. Then any instance can serve any client — stickiness is no longer required. This is the more scalable architecture for large deployments.

</details>

<br>

**Q8: What is backpressure in a WebSocket server and how do you handle a slow client?**

<details>
<summary>💡 Show Answer</summary>

Backpressure occurs when the server is producing messages faster than a client can consume them. If you buffer unlimited messages for a slow client, the server's memory grows unbounded and can exhaust resources. Handling strategies: implement a bounded per-client send queue and drop messages when the queue is full (acceptable for live feeds where stale data is useless). For critical messages, implement a slow-consumer timeout: if a client's send buffer exceeds a threshold or a write blocks for longer than a timeout, disconnect the client. In Python asyncio, if `websocket.send_json()` blocks because the client's TCP receive buffer is full, you can use `asyncio.wait_for()` with a timeout around the send call and close the connection on timeout.

</details>

<br>

**Q9: How does the FastAPI WebSocket server handle the case where a client disconnects without sending a close frame?**

<details>
<summary>💡 Show Answer</summary>

FastAPI raises a `WebSocketDisconnect` exception when it detects the connection has been closed, either by a proper close frame or by a dropped TCP connection. Your handler must catch this exception in the `try/except` block and clean up: remove the connection from the room's connection list, broadcast a disconnect notification to the room, and cancel any background tasks (like a keepalive task) associated with that connection. If you do not catch `WebSocketDisconnect`, the connection reference stays in your `ConnectionManager` data structure and future broadcast attempts to that dead connection will raise exceptions. Always pair `connect()` with cleanup in a `finally` block or a `WebSocketDisconnect` handler.

</details>

<br>

**Q10: When would you choose WebSocket over SSE for a live dashboard showing server metrics?**

<details>
<summary>�Title Show Answer</summary>

For a read-only metrics dashboard where the server pushes data and the browser only displays it, SSE is the better choice — it is simpler, works over standard HTTP without protocol upgrades, has built-in auto-reconnect, and does not require sticky sessions. Choose WebSocket for the same dashboard only if: the dashboard needs interactive controls that send data back (e.g., change the sampling rate, subscribe to different metrics in real time), or you need binary data (compressed metrics payloads), or you are already using WebSocket for other features and want a single connection. The rule of thumb: use the simplest technology that meets the requirement. SSE handles one-way push. WebSocket handles bidirectional communication.

</details>

# 🔹 Advanced Level Questions (5+ Years)

**Q11: Design a WebSocket-based collaborative text editor that handles concurrent edits from multiple users.**

<details>
<summary>💡 Show Answer</summary>

The core challenge is conflict resolution when two users edit the same position simultaneously. There are two main approaches. Operational Transformation (OT): each edit is an operation (insert at position, delete at position). Operations are transformed against concurrent operations to remain consistent — if Alice inserts at position 5 and Bob simultaneously inserts at position 3, Alice's operation is transformed to insert at position 6 (adjusted for Bob's insert). This is what Google Docs uses. Conflict-free Replicated Data Types (CRDTs): the document is represented as a data structure where all concurrent operations commute — order does not matter and there are no conflicts by definition. Automerge and Yjs are production CRDT libraries. The WebSocket layer broadcasts operations to all connected clients in real time. Store the full operation log in Redis or a database for new client catchup and undo/redo.

</details>

<br>

**Q12: How would you implement WebSocket connection limits and resource quotas to prevent abuse?**

<details>
<summary>💡 Show Answer</summary>

At the connection level: enforce a maximum concurrent connections per user (tracked in Redis with an atomic increment before accepting). If the limit is exceeded, reject the connection with close code 1008. At the message level: rate-limit incoming messages per connection using a token bucket tracked in connection state — drop or close connections that exceed the message rate. At the server level: configure a maximum total connections per instance and emit a metric when approaching the limit so autoscaling triggers before the service degrades. Authentication must happen before fully accepting the connection into the pool — reject unauthenticated connections before adding them to the connection manager. Also implement connection age limits: close connections that have been open beyond a maximum lifetime (e.g., 24 hours) and require re-authentication.

</details>

<br>

**Q13: How do you debug a WebSocket connection that works in development but drops frequently in production?**

<details>
<summary>💡 Show Answer</summary>

The most common production-specific culprits in order: First, load balancer timeout — most AWS ALBs and Nginx configs have an idle connection timeout (60 seconds by default on ALB). If no data flows for that period, the load balancer closes the TCP connection silently. Fix: tune the LB idle timeout to longer than your ping interval, and/or ensure your ping keepalive runs more frequently than the LB timeout. Second, NAT gateway timeout — home and mobile NATs drop idle UDP/TCP flows. Same fix: frequent pings. Third, sticky session misconfiguration — the reconnect lands on a different instance that has no session state. Fix: externalize state to Redis. Fourth, proxy buffering — an intermediate proxy buffers WebSocket frames, causing them to arrive in batches or not at all. Fix: set `proxy_buffering off` and `proxy_read_timeout` appropriately in Nginx. Use close code analysis from logs to distinguish graceful closes (1000, 1001) from abnormal ones (1006) — 1006 in production almost always points to a timeout or proxy issue.

</details>
